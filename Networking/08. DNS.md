# DNS — Domain Name System

DNS is the system that translates human-readable hostnames into IP addresses.
Humans remember names — computers use numbers. DNS bridges that gap, handling
billions of lookups per day across a distributed, hierarchical infrastructure.

---

## 1. Core definitions

### DNS (Domain Name System)

A distributed, hierarchical system that resolves hostnames (e.g. `google.com`)
to IP addresses (e.g. `142.250.185.68`), allowing humans to use memorable names
while the network continues to route using IP addresses. Operates at layer 7
(Application) using port 53 — UDP for standard queries, TCP for large responses.

---

### Recursive resolver

The DNS server your machine is configured to use — typically provided by your
ISP or a public service such as Google (`8.8.8.8`) or Cloudflare (`1.1.1.1`).
The recursive resolver does the heavy lifting on your behalf: it queries the
root servers, TLD servers, and authoritative name servers in sequence, caches
the result, and returns the answer to your machine.

---

### Root servers

The top of the DNS hierarchy. There are 13 sets of root servers worldwide
(labeled a through m), backed by hundreds of physical machines using anycast
routing. Root servers do not know the IP address of any specific domain — they
know which TLD servers are responsible for each top-level domain (`.com`,
`.org`, `.ke` etc.) and direct queries accordingly.

---

### TLD server (Top Level Domain server)

Responsible for a specific domain extension. The `.com` TLD server knows which
authoritative name servers are responsible for every `.com` domain, but does
not hold the actual DNS records. It directs the recursive resolver to the
correct authoritative server.

---

### Authoritative name server

The final authority for a specific domain. Holds the actual DNS records —
the definitive answer to queries about that domain. When you register a domain,
you configure which servers are authoritative for it.

---

### TTL (Time To Live)

A value in seconds attached to every DNS record that tells resolvers how long
to cache the answer before querying again.

```
Low TTL  →  changes propagate quickly, but more DNS traffic
High TTL →  less DNS traffic, but changes take longer to propagate worldwide
```

---

### hosts file

A local file on every machine that maps hostnames to IP addresses, checked
before DNS on most operating systems. Originally the only hostname resolution
mechanism before DNS existed.

```
Linux / macOS:   /etc/hosts
Windows:         C:\Windows\System32\drivers\etc\hosts
```

## 2. DNS hierarchy

```
                        . (root)
                       /|\
                    .com .org .ke ...      ← TLD servers
                   /    \
            google.com  amazon.com ...     ← Authoritative name servers
           /
     www.google.com                        ← Individual hostname records
```

---

## 3. DNS resolution — full walkthrough

When you type `www.google.com` into your browser:

```
Step 1 — Browser cache
         Has the browser resolved this recently?
         If yes → use cached answer, done.

Step 2 — OS cache and hosts file
         Has the OS resolved this recently, or is it in /etc/hosts?
         If yes → use cached answer, done.

Step 3 — Recursive resolver
         Your machine asks its configured DNS server (e.g. 8.8.8.8).
         Does the resolver have a cached answer?
         If yes → return cached answer, done.

Step 4 — Root server
         Recursive resolver asks a root server:
         "Who handles .com?"
         Root server replies: "Ask the .com TLD server at x.x.x.x"

Step 5 — TLD server
         Recursive resolver asks the .com TLD server:
         "Who is authoritative for google.com?"
         TLD server replies: "Ask Google's name server at y.y.y.y"

Step 6 — Authoritative name server
         Recursive resolver asks Google's authoritative server:
         "What is the IP address of www.google.com?"
         Authoritative server replies: "142.250.185.68"

Step 7 — Response returned and cached
         Recursive resolver returns the answer to your machine
         and caches it for the duration of the TTL.

Step 8 — Connection established
         Your browser connects to 142.250.185.68.
```

This entire process typically completes in under 100 milliseconds.

## 4. DNS record types

| Record | Full name          | Purpose                                                              |
|--------|--------------------|----------------------------------------------------------------------|
| A      | Address            | Maps a hostname to an IPv4 address. `google.com → 142.250.185.68`   |
| AAAA   | IPv6 Address       | Maps a hostname to an IPv6 address                                   |
| CNAME  | Canonical Name     | Alias — maps one hostname to another hostname. `www.example.com → example.com` |
| MX     | Mail Exchange      | Specifies the mail server responsible for receiving email for a domain |
| NS     | Name Server        | Identifies the authoritative name servers for a domain               |
| TXT    | Text               | Stores arbitrary text — used for domain verification, SPF records, and security configurations |
| PTR    | Pointer            | Reverse DNS — maps an IP address back to a hostname                  |
| SOA    | Start of Authority | Contains administrative information about a DNS zone — primary name server, contact email, serial number |

## 5. Practical DNS tools

### dig (Domain Information Groper)

The standard DNS query tool on Linux and macOS.

```bash
dig google.com              # query the A record for google.com
dig google.com MX           # query the MX records
dig google.com NS           # query the authoritative name servers
dig google.com AAAA         # query the IPv6 address record
dig @8.8.8.8 google.com     # query using Google's DNS server specifically
dig +short google.com       # return only the IP address, no extra output
dig +trace google.com       # show the full resolution path (root → TLD → authoritative)
```

### nslookup

Available on Linux, macOS, and Windows.

```bash
nslookup google.com                  # basic A record lookup
nslookup -type=MX google.com         # query MX records
nslookup -type=NS google.com         # query name server records
nslookup google.com 8.8.8.8          # query using a specific DNS server
```

---

## 6. Key distinctions

- **A vs AAAA** — A records are for IPv4, AAAA records are for IPv6. Both map
  a hostname to an address but at different protocol versions.

- **CNAME vs A** — A CNAME points to another hostname, not directly to an IP
  address. The resolver must then look up that hostname too. A records point
  directly to an IP. You cannot use a CNAME at the root of a domain
  (e.g. `example.com` itself) — only on subdomains.

- **MX vs A** — MX records do not contain IP addresses — they contain
  hostnames of mail servers. The resolver must then look up the A record for
  that mail server hostname separately.

- **UDP vs TCP for DNS** — port 53 uses UDP for standard queries because it is
  fast and most DNS responses are small. TCP is used when the response exceeds
  512 bytes — for example, zone transfers between name servers or very large
  record sets.
