# TCP and UDP — Transport Layer

The transport layer (OSI layer 4) is responsible for end-to-end delivery of
data between applications. Two protocols dominate: TCP for reliable delivery
and UDP for fast, lightweight delivery. Every application on the internet uses
one or the other.

---

## 1. Core distinction

```
TCP  =  registered post — tracked, signed for, re-sent if lost
UDP  =  dropping a flyer through a letterbox — fast, no confirmation
```

| Feature               | TCP                        | UDP                          |
|-----------------------|----------------------------|------------------------------|
| Connection            | Connection-oriented        | Connectionless               |
| Reliability           | Guaranteed delivery        | No guarantees                |
| Ordering              | Data arrives in order      | Order not guaranteed         |
| Error checking        | Yes — retransmission       | Checksum only, no retransmit |
| Speed                 | Slower — overhead          | Faster — minimal overhead    |
| Flow control          | Yes — sliding window       | No                           |
| Congestion control    | Yes                        | No                           |
| Header size           | 20 bytes minimum           | 8 bytes                      |
| Use cases             | HTTP, FTP, SSH, email      | DNS, VoIP, streaming, gaming |

---

## 2. TCP — Transmission Control Protocol

TCP (Transmission Control Protocol) provides reliable, ordered,
connection-oriented delivery. It guarantees that every byte arrives, in the
correct order, without corruption — through a formal connection process,
acknowledgements, and retransmission of lost data.

---

### The three-way handshake

Before any data is exchanged, TCP establishes a connection using three
messages. This confirms both sides are reachable and ready to communicate,
and synchronises sequence numbers between them.

```
Client                          Server
  │                               │
  │──── SYN ──────────────────►   │   "I want to connect"
  │                               │
  │   ◄─── SYN-ACK ─────────────  │   "Acknowledged — I am ready"
  │                               │
  │──── ACK ──────────────────►   │   "Confirmed — connection established"
  │                               │
  │         [data exchange]       │
```

- **SYN** (Synchronise) — client initiates the connection and sends its
  starting sequence number
- **SYN-ACK** (Synchronise-Acknowledge) — server confirms receipt and sends
  its own sequence number
- **ACK** (Acknowledge) — client confirms the server's sequence number;
  connection is now established

---

### The four-way termination

Closing a TCP connection requires four messages — each side independently
closes its half of the connection:

```
Client                          Server
  │──── FIN ──────────────────►  │   "I am done sending"
  │   ◄─── ACK ─────────────────  │   "Acknowledged"
  │   ◄─── FIN ─────────────────  │   "I am also done sending"
  │──── ACK ──────────────────►  │   "Acknowledged — connection closed"
```

---

### Sequence numbers and acknowledgements

Every byte of data in a TCP stream is numbered using sequence numbers. The
receiver sends back an ACK (acknowledgement) confirming which bytes it has
received. If the sender does not receive an ACK within a timeout period, it
retransmits the missing data.

```
Sender:    sends segment — sequence number 1
Receiver:  ACK → "next expected = 2"
Sender:    sends segment — sequence number 2
Receiver:  ACK → "next expected = 3"
...
Sender:    sends segment 5 — lost in transit
Receiver:  timeout → ACK still saying "waiting for 5"
Sender:    retransmits segment 5
Receiver:  ACK → "next expected = 6"
```

---

### TCP flow control — sliding window

Flow control prevents a fast sender from overwhelming a slow receiver. The
receiver advertises a **receive window** — the maximum amount of unacknowledged
data it can buffer at any time. The sender must not exceed this limit.

```
Receive window = 3 segments

Sender has 3 unacknowledged segments in flight at once:
[seg 1] [seg 2] [seg 3] ──► waiting for ACKs before sending more
```

As the receiver processes data and frees buffer space, it increases the window
size — allowing the sender to transmit more. This is the **sliding window**
mechanism.

---

### TCP congestion control

Congestion control prevents the sender from overwhelming intermediate routers
and network links — separate from flow control, which protects the receiver.

TCP adjusts its **congestion window** dynamically:

```
Slow start:          begins small, doubles the window each round trip
                     until a threshold is reached

Congestion avoidance: grows the window linearly (more slowly) after
                     the threshold

Congestion detected:  packet loss detected → window reduced sharply,
(packet loss)         process restarts from slow start or threshold
```

## 3. UDP — User Datagram Protocol

UDP (User Datagram Protocol) provides fast, connectionless, best-effort
delivery. There is no handshake, no sequence numbers, no acknowledgements,
and no retransmission. A datagram is sent and the sender immediately moves on.

```
Client                          Server
  │──── datagram ─────────────►  │   sent — no confirmation
  │──── datagram ─────────────►  │   sent — no confirmation
  │──── datagram ─────────────►  │   sent — no confirmation
```

What arrives, arrives. What is lost, is lost. If reliability is required, the
application layer must implement it. UDP's 8-byte header vs TCP's 20-byte
minimum header means significantly less overhead per packet.

---

## 4. When to use TCP vs UDP

| Scenario                   | Protocol | Reason                                              |
|----------------------------|----------|-----------------------------------------------------|
| Web browsing (HTTP/HTTPS)  | TCP      | Page must arrive complete and in order              |
| File transfer (FTP)        | TCP      | Every byte must arrive intact                       |
| Email (SMTP, IMAP)         | TCP      | Messages must arrive complete                       |
| SSH / remote access        | TCP      | Commands must arrive in order and reliably          |
| DNS queries                | UDP      | Small, single-request queries — speed matters       |
| Video streaming            | UDP      | A dropped frame is better than a pause to re-buffer |
| VoIP / online calls        | UDP      | Latency matters more than perfection                |
| Online gaming              | UDP      | Speed critical — a missed update is acceptable      |
| DHCP                       | UDP      | Client has no IP yet — cannot establish TCP         |

## 5. Ports and sockets

### Port number

A 16-bit number (0–65535) that identifies a specific application on a machine.
The IP address gets data to the right machine — the port number gets it to the
right application on that machine.

```
Port ranges:
0    – 1023   Well-known ports   (HTTP, HTTPS, SSH, DNS etc)
1024 – 49151  Registered ports   (specific applications)
49152– 65535  Ephemeral ports    (temporarily assigned by OS for outgoing connections)
```

---

### Socket

A socket is the combination of an IP address and a port number — it identifies
one specific endpoint of one specific connection.

```
Socket = IP address : port number
Example: 192.168.1.5:51234
```

---

### Socket pair

A complete TCP connection is identified by a socket pair — the source socket
and the destination socket. This four-tuple uniquely identifies every
connection on the internet.

```
Source socket:       192.168.1.5:51234    (your machine, ephemeral port)
Destination socket:  93.184.216.34:443    (web server, HTTPS)

Four-tuple: (src IP, src port, dst IP, dst port)
```

Two connections between the same machines on the same destination port are
always distinguishable because the ephemeral source port on the client side
differs for each connection.

---

### Ephemeral ports

When your machine initiates an outgoing connection, the OS assigns a temporary
source port from the ephemeral range (49152–65535). This port exists only for
the duration of the connection and is released when the connection closes.

---

## 6. TCP flags reference

TCP uses control flags in the header to signal connection state:

| Flag | Name        | Purpose                                      |
|------|-------------|----------------------------------------------|
| SYN  | Synchronise | Initiates a connection, sends sequence number|
| ACK  | Acknowledge | Confirms receipt of data or SYN              |
| FIN  | Finish      | Signals end of data from this side           |
| RST  | Reset       | Abruptly terminates a connection             |
| PSH  | Push        | Tells receiver to pass data to application immediately |
| URG  | Urgent      | Marks data as urgent, process immediately    |
